Schema

What the database actually stores

Ten collections, defined in bus/api/src/models. Before any sizing, one structural fact governs everything below:

The finding that decides the storage answer

Nothing in this schema grows with usage. There is no trip history, no location history, no notification log, no audit trail. Driver.currentLocation is a single embedded point overwritten in place every five seconds. stopArrivals and notifiedStudentIds are cleared on every /trip/start and /trip/stop.

Your database size is therefore a function of headcount alone. A bus running this route for three years costs exactly the same storage as one that ran it yesterday.

The real cost

You are billed for operations, not bytes

Atlas meters throughput. The free tier caps at 100 operations per second; the Flex tier prices in bands up to 500; past that you are on dedicated hardware. So the question that sets your bill is not how much do we store but how many queries per second do we fire.

The answer is: far more than you would expect, because both hot paths run several queries where they need one.

Hot path 1 — the student map poll

StudentDashboardScreen.tsx:31 polls /api/student-auth/bus-location every 5 seconds. Each single poll costs six queries:

requireStudent middleware

1StudentModel.findById— authenticate the bearer token
2CollegeModel.findById— resolve the owning admin
3AdminModel.findById— read one `suspended` boolean

route handler

4StudentModel.findById— duplicate of query 1
5BusModel.findById— route and stops
6DriverModel.findById— live position

6 queries ÷ 5 s = 1.2 ops/sec per student watching the map

Hot path 2 — the driver position write

Worse per head. DriverDashboardScreen.tsx:106 posts to /api/driver/trip/location every 5 seconds, and the handler fires a proximity check on every write:

requireDriver middleware

1DriverModel.findById— authenticate
2CollegeModel.findById— suspension check
3AdminModel.findById— suspension check

route handler

4DriverModel.findById— duplicate of query 1
5driver.save()— write the new position

notifyArrivingSoon · runs on every write

6BusModel.findOne({driver})— find the route
7DriverModel.findById— third read of the same driver
8StudentModel.find({...})— every rider on the bus

8 queries ÷ 5 s = 1.6 ops/sec per driver on a trip

What this means at your scale

Fifty drivers on the morning run generate 80 ops/sec before a single student opens the app. That alone consumes 80% of the free tier's entire budget. Add students and you exceed the free tier at roughly 17 concurrent watchers.

The line that matters

At your target the fixes are worth $36/month — $432 a year. One tier up, at a large university, the same three changes are worth $332/month, or ~$4,000 a year. The work is a day.

Remediation

Three changes, in order of payoff

1

Delete the duplicate student lookup

studentAuth.ts:197 calls StudentModel.findById again for a student the requireStudent middleware already loaded four lines earlier. Attach it to the request and read it. The identical bug is in the driver location handler.

6 → 5 ops
2

Cache the suspension check

Every poll from every user reads colleges and then admins to fetch one boolean that changes perhaps twice a year. A 60-second in-process cache keyed by college id removes two queries from every authenticated request in the system — not just these two paths.

5 → 3 ops
3

Poll every 10 seconds, not 5

A bus does not move meaningfully in five seconds, and the GPS fix underneath is not that precise anyway. One constant in StudentDashboardScreen.tsx:31. Halves every student-side number on this page.

50% of all reads

Together these take the student path from 6 queries every 5 seconds to 3 every 10 — a 4× reduction — and the driver path from 8 to 5. That is the difference between the two lines on the chart.

There is a fourth change worth considering separately, because it is a redesign rather than a fix: stop polling entirely. The drivers already push their position to the server every five seconds, so the data is on the server the moment it exists. Students are polling to discover something you could push to them over FCM — which is already wired up and working. That would take the student read load to approximately zero.

Risks

Three things worth fixing while you are in here

Aadhaar numbers are stored in plaintext

Driver.aadharNumber is a required, unique, /^\d{12}$/-validated string sitting unencrypted in the driver document. That is an Indian national identity number for 55 people, readable by anyone with database access or a backup file, and it is returned by the drivers list endpoint. Under the Aadhaar Act and the DPDP Act this needs field-level encryption at minimum, and a serious answer to whether you need to collect it at all. Nothing in the app appears to use it.

The banner image has no size cap

Driver photos are capped at 400,000 characters by parseImageField in lib/images.ts:11. Banner.imageDataUrl has no equivalent — it is bounded only by the 10 MB Express body limit in app.ts:28. A single 5 MB poster would occupy more space than all 1,000 student records combined, seven times over. Apply the same cap.

Device tokens accumulate

fcmTokens is already the largest field on a student record at 187 B. Sign-in pulls a token off its previous owner, but a user's own stale tokens are only cleaned by scripts/pruneSharedDeviceTokens.ts, run by hand. A student who changes phone three times over a degree carries four tokens and a document half again as large. Schedule the prune, or cap the array.

Method. Document sizes are BSON computed field-by-field from the Mongoose schemas in bus/api/src/models — type byte, field-name CString, length prefix and payload for each field, plus 5 B of document framing. String lengths assume realistic Indian college data: 18-char names, 45-char addresses, 10-digit mobiles, 20-char stop names, 15 stops per route, one 163-character FCM token. Index overhead is estimated at ~46 B per entry per index across the 21 indexes defined in the schemas.

Operation counts were read directly from the route handlers and middleware — studentAuth.ts, driverTrip.ts, lib/suspension.ts — not estimated. Polling intervals are the constants in the shipped app.

Uncertainty. Peak concurrency of 50% is an assumption, not a measurement; the chart shows the full curve so you can substitute your own. Atlas publishes an ops/sec ceiling only for M0 and Flex, so dedicated-tier placement for scenarios C, D and E is inference from vCPU and RAM and should be load-tested before it becomes a budget line.
